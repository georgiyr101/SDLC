## 1. Введение {#1-introduction}

Документ определяет актуальные верифицируемые требования к программному продукту «Трекер финансов» (версия 0.2), уточнённые и утверждённые в результате двух раундов согласования между Исполнителем (Архитектором ПО) и Заказчиком (Product Owner). Система представляет собой кроссплатформенный комплекс из настольного приложения (JavaFX 21), мобильных приложений для Android (Jetpack Compose) и iOS (SwiftUI), а также серверной части на Spring Boot 3 с удалённой базой данных PostgreSQL 16.

### 1.1 Назначение документа {#11-document-purpose}

Спецификация фиксирует требования к поведению и свойствам системы **ЧТО** должна делать система «Трекер финансов». Документ служит единым источником истины для:
- команды разработчиков (Middle Java Developer, Junior Developer);
- приёмочного тестирования и валидации критериев приёмки (Acceptance Criteria);
- Заказчика для контроля согласованного объёма, сроков (4 недели) и сметы ($1 840).

### 1.2 Область применения продукта {#12-product-scope}

Продукт — «Трекер финансов», версия 1.0. Предназначен для повседневного контроля личных финансов, планирования бюджета и предотвращения импульсивных перерасходов.

**Входит в согласованный объём версии 1.0 (Must):**
- регистрация и аутентификация пользователей по JWT с изоляцией данных в PostgreSQL;
- настольный клиент на JavaFX 21, мобильный клиент для Android 10+ и мобильный клиент для iOS 16+ с паритетом базовых функций;
- быстрый вход в мобильные приложения по 4-значному PIN-коду и системной биометрии (FaceID / TouchID / BiometricPrompt);
- мультивалютные счета с точным расчётом баланса в `BigDecimal`;
- журнал доходов и расходов, межсчётные переводы между счетами одной валюты;
- регулярные автоплатежи по расписанию (подписки, аренда, коммуналка) с защитой от дубликатов;
- встроенный каталог 11 базовых категорий и создание собственных категорий с мягкой архивацией;
- детерминированная автокатегоризация по совпадению подстрок в описании;
- модель месячного лимита в % от дохода, указываемая вместе с доходом месяца, с динамическим пересчётом суммы лимита;
- светофорная индикация («Норма» / «Предупреждение» / «Превышен») и системные push-уведомления на смартфонах при достижении 80% и 100% лимита;
- аналитические визуализации: круговая диаграмма распределения трат и помесячное сопоставление доходов/расходов;
- эталонный экспорт выписки в формат CSV (в настольном клиенте).

**Не входит в версию 1.0 (перенесено в релиз 1.1 или бэклог):**
- работа в офлайн-режиме без интернета с локальной синхронизацией;
- веб-клиент в браузере;
- прямая интеграция с банковскими API и парсинг SMS/push от банков;
- мультивалютные переводы с динамической конвертацией по курсам ЦБ;
- учёт кредитов, ипотек, инвестиционных портфелей и налоговых вычетов;
- компоненты машинного обучения (ИИ/МО).

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

Продукт «Трекер финансов» является самостоятельной трёхзвенной кроссплатформенной системой. Сервер приложений Spring Boot 3 и база данных PostgreSQL 16 разворачиваются в Docker-контейнерах на удалённом сервере. Клиентские приложения Desktop (JavaFX), Android и iOS функционируют как тонкие клиенты, взаимодействующие с сервером по защищённому протоколу HTTPS REST API.

```
+-----------------------------------------------------------------+
|                       КЛИЕНТСКИЙ СЛОЙ                           |
|   +------------------+  +-----------------+  +---------------+  |
|   | Desktop (JavaFX) |  | Android Compose |  |  iOS SwiftUI  |  |
|   +--------+---------+  +--------+--------+  +-------+-------+  |
+------------|---------------------|-------------------|----------+
             | HTTPS REST API      | (JSON, Bearer)    |
             +---------------------+-------------------+
                                   |
                                   v
+-----------------------------------------------------------------+
|                        СЕРВЕРНЫЙ СЛОЙ                           |
|       Spring Boot 3 API (Security, Services, Scheduler)         |
+----------------------------------+------------------------------+
                                   | JDBC Connection Pool
                                   v
+-----------------------------------------------------------------+
|                         СЛОЙ ДАННЫХ                             |
|               PostgreSQL 16 (Docker, ACID, Migrations)          |
+-----------------------------------------------------------------+
```

### 2.2 Функции продукта {#22-product-functions}

1. **Управление профилем и безопасность:** регистрация, вход по JWT, быстрый вход по PIN-коду и системной биометрии (FaceID/TouchID/BiometricPrompt).
2. **Счета и баланс:** открытие мультивалютных счетов, точный расчёт остатка в `BigDecimal`, архивация счетов.
3. **Операции:** журнал доходов и расходов, межсчётные переводы, поиск и фильтрация.
4. **Регулярные платежи:** расписание автосписаний подписок и коммунальных платежей с защитой от дублирования (`RecurringPaymentService`).
5. **Категоризация:** 11 базовых категорий, создание пользовательских категорий, автокатегоризация по подстрокам.
6. **Бюджетирование в % от дохода:** фиксация целевого процента трат при внесении дохода месяца, расчёт абсолютной суммы лимита, светофорная индикация и системные push-уведомления при 80% и 100%.
7. **Аналитика:** круговая диаграмма распределения трат и сопоставление доходов/расходов по месяцам.
8. **Обмен данными:** выгрузка выписки в эталонный CSV-файл (на ПК).

### 2.4 Характеристики пользователей {#24-user-characteristics}

- **Владелец личного бюджета:** вносит траты на ходу со смартфона (Android или iPhone), контролирует остаток месячного лимита по светофору и push-уведомлениям, дома на ПК анализирует диаграммы и выгружает CSV.
- **Новый пользователь:** подключает готовые категории из справочника в 1 клик, настраивает PIN-код для быстрого входа.
- **Инженер сопровождения:** администрирует Docker-контейнеры и автоматические бэкапы PostgreSQL.

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}

- **A1:** Компьютер пользователя оснащён JRE 17+ либо используется пакет `jpackage`.
- **A2:** Смартфоны пользователей поддерживают биометрическую аутентификацию либо ввод 4-значного PIN-кода.
- **A3:** Подключение к интернету со скоростью не менее 1 Мбит/с.
- **D1:** Наличие удалённого сервера Linux с установленным Docker Engine.
- **D2:** Участие в разработке Middle-разработчика (80 ч) и Junior-разработчика (24 ч).

## 3. Требования {#3-requirements}

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}

**REQ-INT-001 — Структура навигации клиентов**
- **Statement:** Настольный клиент (JavaFX) и мобильные клиенты (Android и iOS) должны предоставлять разделы: «Обзор», «Операции», «Счета», «Категории», «Бюджет», «Регулярные платежи», «Отчёты». В JavaFX навигация выполняется боковой панелью, в Android — нижней панелью (Bottom Navigation Bar), в iOS — панелью вкладок (Tab Bar).
- **Rationale:** Следование платформа-специфичным гайдлайнам интерфейса при сохранении единого UX.
- **Acceptance Criteria:** Переключение раздела в 1 клик/тап; визуальная подсветка активной вкладки.
- **Verification Method:** Demonstration
- **Priority:** 20 (Must).

**REQ-INT-002 — Форма добавления операции и мобильный ввод**
- **Statement:** Форма добавления операции должна содержать поля: тип (доход / расход / перевод), сумма, дата, счёт списания, категория, описание, а для дохода — поле «Лимит расходов месяца, % от дохода». На Android и iOS формы оптимизированы для ввода одной рукой с автоматическим открытием числовой клавиатуры.
- **Rationale:** Уточнение Раунда 1: перенос формы ввода на смартфонах на 3-ю неделю для обеспечения раннего тестирования Заказчиком.
- **Acceptance Criteria:** Некорректный ввод (сумма ≤ 0, процент < 0 или > 100) подсвечивается ошибкой и блокирует отправку; форма мгновенно валидируется.
- **Verification Method:** Test
- **Priority:** 20 (Must, повышено с 30).

**REQ-INT-009 — Адаптация под сенсорные экраны Android и iOS**
- **Statement:** Все интерактивные элементы управления мобильных клиентов должны иметь габариты сенсорной зоны не менее 48×48 dp на Android и не менее 44×44 pt на iOS, учитывать вырезы экрана (Notch, Dynamic Island) и безопасные зоны (Safe Area Insets).
- **Rationale:** Предотвращение ложных нажатий на смартфонах на ходу.
- **Acceptance Criteria:** Приложение корректно масштабируется на экранах от 4.7" до 6.7" без перекрытия кнопок системными панелями.
- **Verification Method:** Demonstration
- **Priority:** 20 (Must).

#### 3.1.2 Аппаратные интерфейсы {#312-hardware-interfaces}

**REQ-INT-005 — Поддерживаемые экраны и устройства**
- **Statement:** Настольный клиент должен поддерживать разрешение от 1024×720; клиент Android — экраны с минимальной шириной 360 dp; клиент iOS — экраны шириной от 375 pt (iPhone SE 2/3, iPhone 11..16).
- **Rationale:** Гарантия отображения без появления горизонтального скролла на типовом парке устройств.
- **Acceptance Criteria:** Вёрстка не ломается при изменении ориентации на планшетах и смартфонах.
- **Verification Method:** Demonstration
- **Priority:** 20 (Must).

#### 3.1.3 Программные интерфейсы {#313-software-interfaces}

**REQ-INT-006 — Инкапсулированный доступ к PostgreSQL**
- **Statement:** Сервер приложений Spring Boot подключается к удалённой СУБД PostgreSQL 16 через пул HikariCP; прямой сетевой доступ клиентов к порту 5432 заблокирован межсетевым экраном.
- **Rationale:** Архитектурное решение ADR-002, защита целостности базы данных.
- **Acceptance Criteria:** Порт 5432 закрыт от внешнего мира, доступ разрешён только внутри Docker-сети сервера.
- **Verification Method:** Inspection
- **Priority:** 10 (Must).

**REQ-INT-007 — Эталонный формат файлов CSV**
- **Statement:** Настольный клиент должен поддерживать экспорт списка операций в CSV-файл в кодировке UTF-8 со строкой заголовка `Date,Type,Amount,Currency,Account,Category,Description` и разделителем `,` (или `;`).
- **Rationale:** Уточнение Раунда 1: фиксация стабильного эталонного формата для исключения перегрузки парсера.
- **Acceptance Criteria:** Экспортированный файл открывается без искажения кириллицы в Excel и LibreOffice Calc.
- **Verification Method:** Test
- **Priority:** 40 (Must).

**REQ-INT-008 — Единый клиент-серверный REST API**
- **Statement:** Сервер предоставляет клиентам Desktop, Android и iOS унифицированный REST API по протоколу HTTPS с форматом сообщений JSON, версионированием `/api/v1/...` и авторизацией Bearer JWT.
- **Rationale:** Единая кодовая база бэкенда для всех трёх поддерживаемых платформ.
- **Acceptance Criteria:** Документация OpenAPI 3.0 доступна по адресу `/swagger-ui.html`; неавторизованные запросы возвращают HTTP 401.
- **Verification Method:** Test
- **Priority:** 10 (Must).

### 3.2 Функциональные требования {#32-functional}

#### Учётные записи, сессии и безопасность

**REQ-FUNC-024 — Регистрация пользователя**
- **Statement:** Система должна регистрировать пользователя по уникальному адресу электронной почты и паролю длиной не менее 8 символов с обязательным согласием на обработку персональных данных.
- **Rationale:** Разделение данных разных пользователей в мультитенантной базе.
- **Acceptance Criteria:** При повторной регистрации Email возвращается понятная ошибка; пароль валидируется на сложность.
- **Verification Method:** Test
- **Priority:** 10 (Must).

**REQ-FUNC-025 — Авторизация и JWT-токены**
- **Statement:** Вход в систему выполняется по Email/паролю с выдачей пары токенов: Access Token (время жизни 60 минут) и Refresh Token (время жизни 30 дней).
- **Rationale:** Безопасный доступ к API без передачи пароля при каждом сетевом запросе.
- **Acceptance Criteria:** Токены сохраняются в защищённых хранилищах ОС (KeyStore на Android, Keychain на iOS, защищённое хранилище на ПК); пароли хешируются BCrypt (cost 12).
- **Verification Method:** Test
- **Priority:** 10 (Must).

**REQ-SEC-002 — Быстрый биометрический вход и PIN-код на мобильных устройствах**
- **Statement:** Мобильные клиенты Android и iOS должны предоставлять возможность быстрой локальной разблокировки приложения по 4-значному PIN-коду и с помощью системной биометрии (BiometricPrompt / FaceID / TouchID) без повторного ввода пароля от аккаунта.
- **Rationale:** Согласовано в Раунде 2: устранение барьера регулярного ввода длинного пароля при открытии приложения на смартфоне.
- **Acceptance Criteria:** При наличии сохранённого токена приложение запрашивает биометрию/PIN; после 3 неудачных попыток запрашивается мастер-пароль.
- **Verification Method:** Test
- **Priority:** 20 (Must, повышено с Could).

**REQ-FUNC-026 — Синхронизация данных между клиентами**
- **Statement:** Все финансовые транзакции и настройки хранятся на сервере; операции, добавленные на одном устройстве (например, iPhone), должны отображаться на других клиентах (Desktop, Android) не позднее 3 секунд после обновления.
- **Rationale:** Непрерывный актуальный финансовый учёт при смене рабочего устройства.
- **Acceptance Criteria:** Сквозной тест синхронизации подтверждает обновление баланса на всех платформах.
- **Verification Method:** Test
- **Priority:** 10 (Must).

**REQ-FUNC-031 — Функциональный паритет платформ**
- **Statement:** Клиенты Desktop (JavaFX), Android (Compose) и iOS (SwiftUI) должны обладать 100% паритетом по функциям ведения счетов, учёта расходов/доходов, расчёта лимита, регулярных платежей и просмотра аналитики.
- **Rationale:** Равные возможности пользователя независимо от используемого устройства.
- **Acceptance Criteria:** Все бизнес-сценарии доступны на всех трёх клиентских приложениях.
- **Verification Method:** Demonstration
- **Priority:** 10 (Must).

#### Счета и баланс

**REQ-FUNC-001 — Создание и редактирование мультивалютных счетов**
- **Statement:** Пользователь должен иметь возможность создавать счета с указанием названия, типа (наличные, банковская карта, вклад, накопительный счёт), валюты (RUB, BYN, USD, EUR) и начального баланса.
- **Rationale:** Базовый фундамент раздельного учёта денежных средств.
- **Acceptance Criteria:** Счёт отображается в списке активных; создание дубликатов имён отклоняется.
- **Verification Method:** Test
- **Priority:** 10 (Must).

**REQ-FUNC-002 — Точный расчёт баланса в BigDecimal**
- **Statement:** Сервер должен вычислять текущий остаток счёта по формуле: `Начальный_Баланс + Доходы − Расходы + Входящие_Переводы − Исходящие_Переводы`. Все расчёты выполняются строго в `BigDecimal`.
- **Rationale:** Исключение ошибок округления копеек и центов.
- **Acceptance Criteria:** 100% математическая точность расчётов до 2 знаков после запятой в автоматических тестах.
- **Verification Method:** Test
- **Priority:** 10 (Must).

#### Операции и переводы

**REQ-FUNC-004 — Добавление доходных и расходных операций**
- **Statement:** Система должна регистрировать операции доходов и расходов с указанием суммы, даты, счёта, категории и текстового примечания.
- **Rationale:** Основной сценарий фиксации финансовых потоков.
- **Acceptance Criteria:** Операция фиксируется в PostgreSQL, баланс счёта изменяется транзакционно.
- **Verification Method:** Test
- **Priority:** 10 (Must).

**REQ-FUNC-005 — Редактирование и удаление операций**
- **Statement:** Пользователь может отредактировать сумму, категорию или дату ранее внесённой транзакции, либо удалить её с обязательным подтверждением. Балансы счетов и месячные бюджеты пересчитываются сервером автоматически.
- **Rationale:** Коррекция ошибок ввода без рассинхронизации финансовых итогов.
- **Acceptance Criteria:** При удалении расхода баланс счёта увеличивается на удалённую сумму; при отмене диалога операция сохраняется.
- **Verification Method:** Test
- **Priority:** 10 (Must).

**REQ-FUNC-006 — Фильтрация, сортировка и журнал транзакций**
- **Statement:** Система должна отображать постраничный список операций с фильтрацией по счетам, категориям, диапазону дат, типу операции и строковому поиску по описанию.
- **Rationale:** Быстрый поиск чеков и платежей в архиве записей.
- **Acceptance Criteria:** Серверная пагинация (по 50 записей); корректная работа составных фильтров.
- **Verification Method:** Test
- **Priority:** 20 (Must).

**REQ-FUNC-007 — Межсчётные переводы**
- **Statement:** Система должна выполнять перевод средств между двумя счетами пользователя в одной валюте. Перевод уменьшает баланс счёта-источника и увеличивает баланс счёта-приёмника на одну сумму, не учитываясь в доходах или расходах месячного бюджета.
- **Rationale:** Уточнение Раунда 1: декомпозиция на отдельную задачу (4 ч); перемещение собственных денег не изменяет суммарный капитал.
- **Acceptance Criteria:** Перевод выполняется атомарно в одной транзакции PostgreSQL; списание свыше доступного баланса отклоняется.
- **Verification Method:** Test
- **Priority:** 30 (Must).

**REQ-FUNC-008 — Регулярные повторяющиеся платежи по расписанию**
- **Statement:** Система должна позволять настроить график регулярных повторяющихся платежей (ежемесячно в фиксированный день, еженедельно) с указанием счёта, категории и суммы. Планировщик `RecurringPaymentService` на сервере должен автоматически генерировать проводки в заданные даты и исключать повторные списания при перезапуске сервера.
- **Rationale:** Включено в Раунде 2 по требованию Заказчика: автоматизация учёта регулярных подписок, коммунальных платежей и аренды.
- **Acceptance Criteria:** Проводка создаётся в расчётный день; повторный запуск службы в тот же день не дублирует транзакцию.
- **Verification Method:** Test
- **Priority:** 20 (Must, повышено с Could).

#### Категории и автокатегоризация

**REQ-FUNC-009 — Встроенный справочник 11 базовых категорий**
- **Statement:** Система должна предоставлять преднастроенный каталог из 11 категорий: расходы — «Продукты», «Транспорт», «Жильё», «Здоровье», «Развлечения», «Одежда», «Кафе», «Прочее»; доходы — «Зарплата», «Подработка», «Подарки». Пользователь может подключить их выборочно или в 1 клик («Добавить все»).
- **Rationale:** Быстрый старт нового пользователя без ручного заведения структуры расходов.
- **Acceptance Criteria:** Категории доступны сразу после регистрации аккаунта на всех клиентах.
- **Verification Method:** Test
- **Priority:** 20 (Must).

**REQ-FUNC-010 — Пользовательские категории и контроль целостности**
- **Statement:** Пользователь может создавать собственные уникальные категории с выбором иконки и цвета. Запрещено физическое удаление категории, к которой привязаны транзакции — система предлагает перенести операции в другую категорию или архивировать категорию.
- **Rationale:** Защита исторических финансовых отчётов от повреждения.
- **Acceptance Criteria:** Попытка удаления категории с операциями вызывает диалог мягкой архивации.
- **Verification Method:** Test
- **Priority:** 20 (Must).

**REQ-FUNC-011 — Детерминированная автокатегоризация по подстрокам**
- **Statement:** Система должна поддерживать настраиваемые правила назначения категорий по совпадению подстрок в описании операции (например, «Евроопт» → «Продукты», «Яндекс Go» → «Транспорт»).
- **Rationale:** Уточнение Раунда 1: декомпозиция (4 ч) с простой и надёжной строковой логикой без привлечения сложных ML-моделей.
- **Acceptance Criteria:** При сохранении операции с пустым полем категории срабатывает правило автокатегоризации.
- **Verification Method:** Test
- **Priority:** 40 (Must).

#### Лимит расходов месяца (% от дохода) и уведомления

**REQ-FUNC-012 — Задание месячного лимита в % от дохода**
- **Statement:** При фиксации операции дохода пользователь указывает желаемый процент от дохода (от 1 до 100%), который планирует потратить в данном календарном месяце. Значение сохраняется в качестве базы лимита текущего месяца.
- **Rationale:** Архитектурное решение ADR-003: адаптивное финансовое планирование под фактический доход.
- **Acceptance Criteria:** При доходе 120 000 ₽ и проценте 65% базовая сумма лимита составляет 78 000,00 ₽.
- **Verification Method:** Test
- **Priority:** 20 (Must).

**REQ-FUNC-013 — Светофорная индикация статуса бюджета**
- **Statement:** Система должна непрерывно рассчитывать отношение текущих расходов к сумме лимита месяца и отображать визуальный цветовой статус:
  - Расход < 80% лимита: статус «Норма» (зелёный цвет, иконка галочки);
  - 80% ≤ Расход ≤ 100%: статус «Предупреждение» (жёлтый/оранжевый цвет, иконка треугольника);
  - Расход > 100%: статус «Превышен» (красный цвет, иконка Стоп, вывод отрицательного остатка).
- **Rationale:** Наглядный контроль бюджета без необходимости считать остаток в уме.
- **Acceptance Criteria:** Граничные пороги 79.9%, 80.0%, 99.9%, 100.0% корректно переключают цвет на Desktop, Android и iOS.
- **Verification Method:** Test
- **Priority:** 20 (Must).

**REQ-FUNC-014 — Серверный пересчёт лимита и локальные push-уведомления**
- **Statement:** Абсолютная сумма лимита вычисляется на сервере как `Сумма_Доходов_Месяца × (Лимит_% / 100)` в `BigDecimal`. При достижении 80% и 100% лимита мобильные клиенты Android и iOS должны генерировать системные push-уведомления с предупреждением пользователя.
- **Rationale:** Включено в Раунде 2 по согласованию с Заказчиком: оперативное оповещение пользователя о критическом исчерпании лимита трат.
- **Acceptance Criteria:** Внесение расхода, переводящего бюджет через порог 80% или 100%, вызывает локальное системное push-уведомление на смартфоне.
- **Verification Method:** Test
- **Priority:** 30 (Must).

#### Аналитические отчёты и экспорт

**REQ-FUNC-015 — Круговая диаграмма распределения расходов**
- **Statement:** Система должна формировать круговую диаграмму структуры расходов по категориям за выбранный календарный месяц с выводом сумм и процентных долей.
- **Rationale:** Экспресс-анализ основных направлений оттока денежных средств.
- **Acceptance Criteria:** Сумма долей равна 100%; переводы между своими счетами исключены из диаграммы.
- **Verification Method:** Demonstration
- **Priority:** 30 (Must).

**REQ-FUNC-016 — Помесячное сопоставление доходов и расходов**
- **Statement:** Система должна отображать столбчатую диаграмму помесячного соотношения общих доходов и расходов за выбранный годовой период.
- **Rationale:** Анализ финансовой динамики и сезонности накоплений.
- **Acceptance Criteria:** Для каждого месяца отображаются сопоставимые столбцы «Доход» и «Расход».
- **Verification Method:** Demonstration
- **Priority:** 40 (Must).

**REQ-FUNC-018 — Сводная панель «Обзор»**
- **Statement:** Стартовый экран всех клиентов должен содержать сводный блок: суммарный баланс, доходы и расходы текущего месяца, виджет лимита в % со светофорным статусом и круговую диаграмму трат.
- **Rationale:** Отображение финансового состояния сразу после запуска приложения.
- **Acceptance Criteria:** Данные панели полностью согласованы с журналом транзакций.
- **Verification Method:** Demonstration
- **Priority:** 20 (Must).

**REQ-FUNC-020 — Экспорт выписки в CSV (настольный клиент)**
- **Statement:** Настольный клиент должен выполнять экспорт журнала транзакций в файл CSV согласно спецификации REQ-INT-007.
- **Rationale:** Уточнение Раунда 1: декомпозиция (4 ч) для обеспечения возможности сохранения копии архива пользователем.
- **Acceptance Criteria:** Созданный файл содержит корректные заголовки и открывается в Excel без ошибок кодировки.
- **Verification Method:** Test
- **Priority:** 40 (Must).

### 3.3 Качество обслуживания {#33-quality-of-service}

- **REQ-SEC-004 — Изоляция хранения:** Все финансовые данные хранятся на сервере в PostgreSQL; на клиентских устройствах сохраняются только токены доступа. (Must, Приоритет: 10).

- **REQ-SEC-007 — Межпользовательская изоляция:** Доступ к транзакциям, счетам и бюджетам валидируется по идентификатору пользователя из расшифрованного JWT. (Must, Приоритет: 10).
- **REQ-SEC-008 — Закрытый периметр СУБД:** Порт PostgreSQL (5432) недоступен из внешней сети интернет. (Must, Приоритет: 10).

#### 3.3.3 Надёжность {#333-reliability}

- **REQ-REL-001 — ACID-транзакции:** Фиксация проводок только в случае успешного завершения транзакции в PostgreSQL. (Must, Приоритет: 10).
- **REQ-REL-003 — Точность денежного формата:** Хранение в `NUMERIC(19, 2)` и расчёт в `BigDecimal` исключают ошибки округления. (Must, Приоритет: 10).
- **REQ-REL-004 — Устойчивость к сбоям связи:** При потере сети клиент выдаёт понятное сообщение и сохраняет черновик введённых данных. (Must, Приоритет: 20).

#### 3.3.4 Доступность и наблюдаемость {#334-availability}

- **REQ-AVAIL-002 — Доступность API:** Время непрерывной доступности бэкенда — не менее 99.0% в месяц. (Should, Приоритет: 30).
- **REQ-OBS-001 — Защита логов:** В журналах сервера запрещено логирование открытых паролей, номеров карт и персональных данных. (Should, Приоритет: 30).

## 5. Приложения {#5-appendixes}

### Приложение A. Основные сценарии использования (Use Cases)

**UC-1. Добавление расхода на ходу со смартфона (Android или iOS)**
1. Пользователь разблокирует приложение по PIN-коду или FaceID / сканеру отпечатка пальца (REQ-SEC-002).
2. Нажимает кнопку «Добавить расход» и вводит сумму с цифровой клавиатуры.
3. Выбирает категорию «Кафе» и счёт списания «Банковская карта».
4. Нажимает «Сохранить»; клиент отправляет HTTPS POST-запрос с JWT-токеном.
5. Сервер фиксирует транзакцию в PostgreSQL, уменьшает баланс счёта и пересчитывает расход текущего месяца.
6. Экран мгновенно обновляет виджет баланса и индикатор остатка лимита месяца.

**UC-2. Внесение дохода и установка месячного лимита в %**
1. Пользователь выбирает тип операции «Доход».
2. Вводит сумму дохода 100 000 ₽, дату и счёт зачисления.
3. В поле «Лимит расходов месяца, % от дохода» указывает 70%.
4. Сервер сохраняет доход и фиксирует для месяца базу лимита в размере 70 000,00 ₽ (REQ-FUNC-012..014).
5. На Desktop, Android и iOS индикатор бюджета окрашивается в зелёный цвет со статусом «Норма».

**UC-3. Превышение порога трат и получение push-уведомления**
1. В течение месяца сумма расходов пользователя достигает 56 500 ₽ (80.7% от установленного лимита 70 000 ₽).
2. Сервер фиксирует переход порога 80%; статус бюджета переключается на жёлтый «Предупреждение».
3. Служба `BudgetNotificationService` отправляет системное push-уведомление на смартфон пользователя: *«Внимание: израсходовано более 80% месячного лимита!»* (REQ-FUNC-014).
4. Пользователь видит предупреждение и корректирует структуру расходов.

**UC-4. Автоматическое списание регулярного платежа**
1. Пользователь настраивает ежемесячное списание 500 ₽ на категорию «Подписки» 1-го числа каждого месяца.
2. В 03:00 1-го числа серверный планировщик `RecurringPaymentService` запускает процедуру начисления.
3. Сервер создаёт расходную операцию, списывает 500 ₽ со счёта и проверяет флаг выполнения, исключая повторное списание при перезагрузке сервера (REQ-FUNC-008).
